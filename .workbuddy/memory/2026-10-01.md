## ⭐ 本轮最有价值的发现：R014 的**四层误报**逐个拆掉

R014（凭据泄露，0 额外请求）本轮连续暴露 4 个层次的判据缺陷，都是**只有拿到真实站点语料才会暴露**的：

1. **把 reCAPTCHA site key 当凭据**（5.3 中危）。site key 设计上要嵌在前端给浏览器用。
2. **修正方向本身错了**：一度按「整类 `public: true`」处理，但查证后确认
   **reCAPTCHA 的 site key 与 secret key 取值形态完全相同**（Google 官方口径，都是 40 位 `6L…`）
   → 整类打 public = 站点真泄了 **secret key 也会被静默摘掉**，属**失败方向不安全**。
   正解：`ambiguous: true` + 按命中上下文逐条判定，同类别内只要有一条无法确证**整类都不降级**。
3. **上下文覆盖不足**：站点用 **JS 配置对象**配置 reCAPTCHA
   （`GOOGLE_RECAPTCHA:{PROD_V2:"6L…", PROD_V3:"6L…"}`），既不写 `grecaptcha(` 也不写
   `data-sitekey` → 补上下文正则，并把判定窗口收窄（窗口一大，「隔半页的裸 key」会被框进来，
   fail-closed 失效 —— 这条已写进 MEMORY）。
4. **被 base64 内联 SVG 的随机字符流命中**：`www.lenovomm.com` 5 处 `6L…` 全落在
   `data:image/svg+xml;base64,…` 里，整页 `recaptcha` 出现 **0 次**。→ 新增
   **「取值必须独立（分隔 / 粘连判定）」** 通用过滤 —— **任何特征正则都可能踩这个坑**，
   不止 reCAPTCHA。

附带修：`_build_p1_data.py` 是 `secret_patterns.json` 的**整体覆盖式生成器**，
只改产物不改生成器 → 下次 rebuild 静默退回旧判据；已把标注打进生成器映射表 +
**往返证明**（rebuild 一轮逐条比对，不一致回滚报错）。
另发现靶场夹具 bug：`_SITEKEY = "6L" + "aB1_-"*9 + "aB"` 实际 **49 字符**（注释写 40），
被新过滤规则判成「粘连」而炸掉整批断言 → 修为恰好 40。
