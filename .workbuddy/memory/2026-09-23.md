### 三个必须处理的陷阱（详见 HANDBOOK 十五）

1. **SystemExit 会静默杀死请求线程**：`run_check`/合规闸用 `sys.exit(2)`，而
   `SystemExit` 继承 `BaseException`、`socketserver` 只捕 `Exception` → 请求线程
   静默结束、客户端收空响应。**必须先知道这件事**，否则会以为「前端没反应」去查 JS
2. **只给退出码 = 用户看不到原因**：合规闸 `print(reason, stderr); sys.exit(2)`
   把原因与机器码**分开传** → 界面只显示「合规闸拒绝（exit 2）」。修后实测回出
   「目标 'evil.example.com' 不在授权范围（来源 --scope）内」
3. **界面自律钳制**：`interval≥6s` / `max_requests≤10` 强制钳并回显 `clamps`；
   靶场用 **monkeypatch `webui.MIN_INTERVAL`** 改小值，不在生产代码开环境变量后门

## Web 控制台 UI 第二轮改造（按《布局/视觉/交互/细节/合规》全量方案）

第二轮方案把界面推到 **8 级信息层级**，并把原「阶段1 扫描任务驾驶舱」
**拆成 4 张独立卡片**：

`顶部态势 → 合规授权入口 → 流程导航 → 漏洞统计概览 → 任务操作区 →
授权资产列表 → 实时日志 → 高危利用模块`

改动仍是 `webui.py` 的 PAGE（1185 → 1562 行），另加两处后端契约扩展。

### ⭐ 最重要的设计决定：进度与门禁分开建模

流程导航节点同时承载「走到哪了」和「能不能进」。第一版把「前置未满足」
也写成 `state="locked"` → **「没做过」和「做了被锁」在数据上无法区分**，
正是闭环纪律里反复防的那类语义塌缩。改成三个独立维度：

- `state`（pending/running/done/locked）= 进度，**刻意不撒谎**
- `gate` + `need` = 能否进入 + 缺什么
- `hot` = 高危节点（前端据以上橙色），危险程度也是独立维度

前端 `gated = (gate === false) || (state === 'locked' && !已解锁)`。

### 两个「取了正确数据、却印出错结论」的新变体

1. **后端字段缺失 → 前端印假事实**：界面写「排除项 `m.excluded` 条不计入风险」，
   但 `_risk_metrics` 没返回该字段 → `undefined || 0` → 稳定显示**「排除项 0 条」**，
   而会话里实际有 128 条。**无任何报错**。已补后端字段 + 靶场断言。
2. **主题标签没跟着持久化走**：浅色偏好存了 localStorage，但按钮文案只在
   `toggle_theme()` 里改 → 刷新后「页面是浅色、按钮还写深色」。
   抽出 `sync_theme_btn()`，启动即同步。

### 一个纯前端报废级坑

**内联 onclick 不能传 `JSON.stringify` 的值**：会生成
`onclick="flow_goto('init',"pending")"` —— 双引号提前闭合属性，整段 JS 报废。
改为内联只传 key，其余字段从 `ST.flow` 反查。

  超限部分根本不绘制 → 截图是纯背景色，极易误读成「布局空白」。
  控制在 ≤3500px。**三张截图字节数完全相同（都是 6156）就是「全没渲染」的信号**

  报了恰好 65536 字节，真实页面是 85726，一度以为服务端在 64KiB 截断响应。
  校验完整性要落到文件（`-o file` + `wc -c` + 查 `</html>`）
- **浅色主题要看真实数据**：`file://` 注入 light class 只能验配色（跨源 fetch 被
